# Уровень Core {#arch_core}

На данной странице приведено описание уровня Core.

На уровне Core находятся компоненты, состав которых может быть разным,
в зависимости от настроенного профиля. Как правило, на этом уровне
представлены компоненты, реализующие определённые прикладные конструкции
(например, ECS или управление ресурсами). Это отличает уровень Core от
уровня Platform, где компоненты имеют более общее назначение и в теории
могут быть использованы за пределами (домена) игрового движка.

Уровень Core является основанием, на котором построен уровень Plugin,
потому что в нём обявлены основные интерфейсы и точки встраивания,
используемые в плагинах.

## Компоненты уровня Core

### Assets

Компонент Assets предназначен для чтения и записи данных в определённом
формате. Данный компонент реализует синтаксис, но не семантику, то есть
не отвечает за разбор и интерпретацию самих данных, а реализует лишь формат.

Необходимо как минимум 2 формата: производительный и удобный для разработки.
Производительный формат должен обеспечивать минимальные накладные расходы на
разбор. Удобный для разработки формат должен поддерживать простое изменение и,
желательно, быть понятным для чтения человеком.

В качестве производительного формата выбран FlatBuffers. Это бинарный формат,
поэтому программный разбор достаточно быстр, а сохраняемые данные достаточно
компактны. Главным достоинством FlatBuffers является "плоскость" - это значит,
что для разбора не требуется выделять дополнительную память, кроме памяти под
сами разбираемые данные. Данный формат является оснонвным для движка, так что
остальные компоненты используют именно FlatBuffers. Если данные имеют другой
формат, то их нужно сконвертировать (возможно, на лету) в основной формат
перед передачей в другие компоненты движка.

В качестве удобного для разработки формата выбран JSON. Его удобство заключается
в том, что это текстовый формат, и поэтому он может быть прочитан человеком.
Также в FlatBuffers есть встроенная конвертация в/из JSON, что позволяет на лету
преобразовывать JSON в FlatBuffers. Это добавляет накладные расходы на конвертацию,
поэтому формат JSON рекомендуется для использования только во время разработки,
а не в финальных сборках проекта.

#### Устройство ассетов

**Ассет (asset)** - в терминологии движка - это пакеты данных, имеющих описанную
здесь структуру, независимо от содержания.

Ассеты представляют собой контейнеры для данных. В каждом ассете хранится
64-битный идентификатор типа (о смысле которого компонент Assets ничего не знает)
и массив байтов полезной нагрузки. Так как компонент Assets не знает о специфике
данных, то там могут быть как пользовательские данные, так и вложенный
объект FlatBuffers/JSON, интерпретация которого находится за пределами зоны
ответственности данного компонента.

Помимо описанных выше данных, ассеты могут хранить список вложенных дочерних
ассетов. Такое устройство позволяет компоновать ассеты в древовидную структуру
и определять сложные пользовательские форматы данных, например, для описания
игровых сцен.

Вложенные ассеты могут быть представлены либо в виде упорядоченного массива
(тогда обращение к ним будет по индексам, начиная с 0), либо в виде ассоциативного
массива (тогда обращение к ним будет по уникальным в рамках массива строковым
именам). Ассет сохраняет признак использования того или иного способа хранения
вложенных ассетов.

Итоговая схема ассетов в FlatBuffers имеет следующий вид:

```
table AssetData
{
     type_id:  uint64;
     data:     [ubyte]   (required);
}

table Asset
{
     name:     string    (key); // может быть пустым, если у родителя is_array = true
     is_array: bool = false;
     content:  AssetData;
     children: [Asset];
}
```

_Примечание:_ Для FlatBuffers данные (AssetData::data) всегда имеют выравнивание
как у типа `std::max_align_t`. А для JSON data может быть как массивом чисел, где
каждое число представляет один байт, так и строкой (если пользователь произвёл
глубокую конвертацию, см. ниже), в которой содержится вложенный JSON.

При сохранении в файл всегда записывается версия компонента Assets (он имеет
собственное версионирование), чтобы проверять совместимость при чтении. Также могут
быть записаны дополнительные данные, необходимые для корректного разбора ассета в
текущем формате. Движок оставляет возможность для добавления других форматов ассетов,
при условии, что они будут конвертироваться в основной формат (FlatBuffers).

#### Программный интерфейс

Представленные ниже интерфейсы реализованы как для FlatBuffers, так и для JSON.

* **[IAssetReader](@ref _16nar::assets::IAssetReader)** - интерфейс для чтения
древовидной структуры ассетов. Он позволяет получать описанную выше информацию
и перемещаться по дереву вложенных ассетов.
* **[IAssetWriter](@ref _16nar::assets::IAssetWriter)** - интерфейс для записи
древовидной структуры ассетов. Запись осуществляется в порядке от вложенных
ассетов к родительским, так как при записи родительского ассета указываются
его дочерние ассеты.
* **[IAssetFileProcessor](@ref _16nar::assets::IAssetFileProcessor)** - интерфейс
обработчика файлов ассетов. Формат хранения ассета в файле может требовать
определённой логики для разбора, и эта логика скрыта за данным интерфейсом.
Также он является фабрикой, создающей `IAssetReader` и `IAssetWriter` для
нужного формата.
* **[IAssetDataConvertor](@ref _16nar::assets::IAssetDataConvertor)** - интефрейс
для конвертации данных ассетов из произвольного формата в основной и наоборот.
Данный интерфейс оперирует `AssetData` и проводит конвертацию на основе типа.
Обычно в финальных версиях проекта подобная конвертация не нужна, так как все
данные в основном формате. Этот интерфейс больше предназначен для разработки.
Так, существует реализация для конвертации из JSON в FlatBuffers и наоборот,
при этом используются стандартные средства FlatBuffers.

Существуют классы для работы с деревьями вложенных ассетов.

* **[IAssetVisitor](@ref _16nar::assets::IAssetVisitor)** - интефрейс для
выполнения действий при разборе дерева ассетов. Он представляет собой
паттерн "Посетитель (Visitor)" и обычно используется в связке с `AssetIterator`
(см. далее). `IAssetVisitor` нужен для разбора сложных структур ассетов и
выполнения действий на определённых этапах разбора. Например, для конвертации
сложной структуры ассетов в другой формат может вызываться метод `visit()` при
переходе к новому поддереву, потому что оно требует особой логики обработки.
* **[AssetIterator](@ref _16nar::assets::AssetIterator)** - класс, который
предоставляет удобный API для прохода по дереву ассетов и выполнения нужных
проверок. Это лёгкая обёртка над `IAssetReader` и `IAssetVisitor`, которая
позволяет проходить по узлам дерева и вызывать действия.

Использование `AssetIterator` при обходе конкретных сложных структур ассетов
позволяет определить их структуру прямо в коде. Например, следующий код
определяет структуру ассета с двумя вложенными поддеревьями: массив subtree1
(обязательный) и ассоциативный массив subtree2 (опциаональный).
```
     assets::AssetIterator iter{ ... };
     iter
          .call( Actions::Start ) // вызов IAssetVisitor с действием Actions::Start
          .go( "subtree1" )
               .check_array( true )
               .call( Actions::Subtree1Start )
               .for_each( /* some lamda 1 */ )
               .up();
          if ( iter.go_opt( "subtree2" ) )
          {
               iter
                    .check_array( false )
                    .call( Actions::Subtree2Start )
                    .for_each( /* some lamda 2 */ )
                    .up();
          }
```

### Resources

Компонент Resources предназначен для работы с ресурсами.

**Ресурс (resource)** - в терминологии движка - это часть приложения, которая
хранится отдельно от программного кода и является необходимой для работы
приложения.

Ресурсы хранятся в виде ассетов из компонента Assets. Компонент Resources
отвечает за загрузку и выгрузку ресурсов, а также за управление их
зависимостями. При этом, он не определяет конкретные типы ресурсов, а лишь
предоставляет итерфейсы, чтобы пользователи компонента могли сами определить
ресурсы и использовать их под общим интерфейсом.

#### Хранение ресурсов

Ресурсы обычно состоят из данных и метаданных. Метаданные описывают параметры
загрузки и зависимости ресурсов, а данные несут саму полезную нагрузку.

Ресурсы могут храниться как в распакованном виде, так и в составе специальных
пакетов. Каждый пакет состоит из 2 файлов: файл ассета с заголовком и бинарный
файл с данными.

Бинарный файл состоит из участков фиксированного размера, называемых **чанками**.
Они сделаны таким образом, чтобы отображать в память некоторое количество чанков
при чтении ресурсов. При использовании сжатия каждый чанк сжимается независимо.
Каждый ресурс в пакете должен начинаться с нового чанка.

Заголовок содержит минимум информации о каждом ресурсе пакета: имя, тип (только
для метаданных), номер чанка, размер в пакете и размер в памяти (может быть
не равен размеру в пакете из-за сжатия).

_Пример:_ Допустим, существует ресурс текстуры. В метаданных может храниться
структура с описанием размеров текстуры, параметров фильтрации и др. В данных
хранится информация о пикселях. Если ресурс хранится в распакованном виде, то
может быть 2 файла: файл ассета с метаданными и PNG-файл с данными. Если ресурс
хранится в пакете, то в заголовке пакета будет 2 записи: о метаданных и о данных.
А в бинарном файле будет минимум 2 чанка: в одном будет структура метаданных,
а в другом - данные текстуры.

При загрузке распакованных ресурсов можно просто открывать нужные файлы, а при
использовании пакетов ресурсов необходимо предварительно подключить требуемые
пакеты, чтобы из них можно было загружать ресурсы.

#### Программный интерфейс

Для работы с ресурсами предусмотрены следующие классы.

* **[UnifiedStorage](@ref _16nar::resources::UnifiedStorage)** - класс
унифицированного хранилища, который позволяет работать в двух режимах:
распакованные ресурсы или пакеты. Данный класс позволяет подключать
пакеты (в режиме использования пакетов), а также поулчать сырые данные
(читать отдельные файлы или чанки пакетов) без разбора их содержания.
* **[ResourcePkgVisitor](@ref _16nar::resources::ResourcePkgVisitor)** - класс,
реализующий интерфейс `IAssetVisitor` из компонента Assets и определяющий
структуру ассета в заголовке пакета ресурсов.
* **[IResourceReader](@ref _16nar::resources::IResourceReader)** - интерфейс
для чтения данных ресурсов. Он предназначен для выполнения необходимых
преобразований над сырыми данными, получаемыми из `UnifiedStorage`.
Например, если из `UnifiedStorage` считан PNG-файл, то реализация этого
интерфейса может преобразовать его данные в пиксели, пригодные для отрисовки.
* **[IResourceProcessor](@ref _16nar::resources::IResourceProcessor)** - интерфейс
для обработки ресурсов, в частности, при их загрузке. Данный интерфейс
скрывает за собой специфику поэтапной загрузки сложных ресурсов. Например,
для шейдерных программ, состоящих из нескольких файлов, реализация этого
интерфейса может управлять контекстом загрузки шейдерной программы.
* **[IResourceLoader](@ref _16nar::resources::IResourceLoader)** - интерфейс
для управления загрузкой ресурсов. Предполагается, что реализация будет
читать метаданные, а затем на их основе вызывать (потенциально разные экземпляры)
`IResourceReader` для чтения данных и передачу в `IResourceProcessor`.
* **[IResourceManager](@ref _16nar::resources::IResourceManager)** - интерфейс
для управления загруженными ресурсами со стороны остального движка. Данный
интерфейс является точкой входа для использования ресурсов прикладной логикой.

Описанные выше интерфейсы могут использоваться как в проектах на движке, так
и в инструментарии движка для конвертаций и других преобразований ресурсов.
Реализации этих интерфейсов для использования в проектах на движке и содержащие
прикладную логику (например, загрузку текстур в GPU), должны быть на уровне
Plugin.

В коде плагинов `IResourceManager` и `IResourceProcessor` могут быть
реализованы одним и тем же классом. Так удобнее разделять контекст загрузки
ресурсов и сохранения её результатов, не вынося детали реализации за пределы
этих интерфейсов.
