# Уровень Platform {#arch_platform}

На данной странице приведено описание уровня Platform.

На уровне Platform находится базовый функционал, необходимый как уровню Core,
так и уровню Plugin. Компоненты уровня Platform разработаны с целью максимально
широкого использования и не проектировались под определённые профили движка.

Уровень Platform может конфигурироваться, но, в отличие от уровня Core,
это происходит не столько для выбора того или иного архитектурного стиля
движка, сколько для включения поддержки различных системных функций, которые
могут быть или не быть на разных системах (отображение файлов, аппаратное
ускорение и др.).

## Компоненты уровня Platform

### Logger

Компонент Logger предоставляет функции для вывода диагностической информации в
журнал.

Основным классом для вывода сообщений в журнал является синглтон
**[Logger](@ref _16nar::logger::Logger)**. Он позволяет выводить сообщения в
описанном выше формате, однако сам не занимается выводом, а делегирует вывод
отдельным объектам, реализующим интерфейс **[ILogWriter](@ref _16nar::logger::ILogWriter)**.
С помощью разных реализаций данного интерфейса можно записывать журнал разными
способами. Пользователь может регистрировать их методом
**[Logger::add_writer()](@ref _16nar::logger::Logger::add_writer(_16nar::logger::Logger::WriterPtr))**.

Реализации интерфейса **[ILogWriter](@ref _16nar::logger::ILogWriter)**:

* **[TerminalLogWriter](@ref _16nar::logger::TerminalLogWriter)** - вывод в терминал
с возможностью цветного вывода.

Сообщения как правило выводятся в следующем формате на английском языке:
```
ГГГГ-ММ-ДД чч:мм:сс [УРОВЕНЬ]: текст сообщения,
```
где `"ГГГГ-ММ-ДД чч:мм:сс"` - дата вывода, `"[УРОВЕНЬ]"` - описанный выше уровень
журналирования. Максимальная длина сообщения - 4096 символов.

Пример сообщения:
```
2026-06-17 14:30:09 [INFO]: Hello, 16nar!
```

#### Уровни журналирования

Существует несколько уровней критичности сообщений, записываемых в журнал,
каджый из которых имеет критичность, выраженную числом:

* **Error (3)** - критические ошибки, препятствующие дальнейшему выполнению требуемых
функций приложения.
* **Warning (5)** - некритические ошибки, не препятствующие дальнейшему выполнению
требуемых функций приложения, но требующие внимания со стороны пользователя.
* **Info (7)** - информационные диагностические сообщения, не сигнализирующие об ошибке.
* **Debug (9)** - отладочные сообщения о деталях реализации какого-либо функционала,
предназначенные для разработчика.

Текущий уровень критичности устанавливается функцией
**[Logger::set_log_level()](@ref _16nar::logger::Logger::set_log_level(_16nar::logger::Logger::LogLevel))**.
В журнал выводятся все сообщения, у которых уровень критичности такой же или
критичнее установленного.

Для вывода сообщений рекомендуется использовать макросы **LOG_16NAR_<УРОВЕНЬ>**
с соответствующим уровнем критичности. Данные макросы вызывают **Logger**
с нужными параметрами. Поддерживается вывод с форматированием строк, как
в `std::printf`.

Пример строки в коде, для вывода в журнал информационного сообщения:
```
LOG_16NAR_INFO( "Hello, %dnar!", 16 );
```

Движок можно собрать с указанием максимального уровня критичности. Тогда
все макросы **LOG_16NAR_<УРОВЕНЬ>**, у которых уровень менее критичен,
чем установленный при сборке, будут определены пустыми, и их вызов не будет
ничего делать. За уровень критичности при сборке отвечает опция **log_level**
в conan и **NARENGINE_LOG_LEVEL** в CMake. Данная опция принимает числовые
значения от 1 до 9 включительно и по умолчанию равна 9.

### Math

В компоненте Math собраны математические структуры и функции, например, для
работы с векторами и матрицами.

Также в данном компоненте есть функции для выполнения битовых операций.

### Memory

Компонент Memory нужен для управления памятью и аллокациями. Объекты,
выделяемые на куче, обычно создаются с разными целями, но их можно
сгруппировать по смыслу и природе аллокаций. Для этого вводится понятие
домена памяти.

**Домен памяти** - объект, представляющий память, доступную для аллокаций.
Сам домен решает, каким образом аллоцируется запрашиваемая память, предоставляя
пользователю `std::pmr::memory_resource`. Домен памяти представлен базовым
классом **[MemoryDomain](@ref _16nar::memory::MemoryDomain)**. В данном
классе предусмотрен подсчёт статистики использования памяти.

Для управления доменами существует класс **[MemoryManager](@ref _16nar::memory::MemoryManager)**.
Он позволяет добавлять пользовательские домены памяти и выстраивать их в
древовидную структуру, где ресурс родительского домена будет источником
памяти (upstream) для дочерних ресурсов. Также менеджер памяти ассоциирует
домены с именами, по которым их можно получить. Менеджер памяти позволяет
очищать память целых поддеревьев доменов (внимание: деструкция объектов
при этом не производится и должна быть заранее выполнена пользователем).

Важно, что для создания менеджера памяти необходим корневой домен памяти,
внутри которого будут производиться все аллокации.

#### Вспомогательные классы для доменов

Для упрощения использования доменов памяти предусмотрены вспомогательные классы:

* **[StatsResourceWrapper](@ref _16nar::memory::StatsResourceWrapper)** - шаблонный
класс-обёртка над стандартным ресурсом памяти, предназначенный для ведения
статистики использования памяти.
* **[ProxyResource](@ref _16nar::memory::ProxyResource)** - класс домена, не
имеющий своего собственного ресурса памяти, а использующий внешний ресурс.
При этом, статистика для него ведётся собственная. Данный класс предназначен,
в первую очередь, для подключения стандартных ресурсов памяти в виде доменов,
т.е. `ProxyResource` может быть использован как адаптер.

### Strings

Компонент Strings предназначен для эффективной работы со строками в движке.
Предполагается, что используются строки в UTF-8.

Итерация по символам строк является нежелательной для производительности,
при этом, многие строки создаются один раз и более не меняются. Это позволяет
заменить строки на их хэш-суммы. Хэш-суммы можно использовать для быстрого
поиска и проверки строк на равенство (при условии, что отсутствуют коллизии хэша).

Для использования хэш-сумм введён класс **[StaticName](@ref _16nar::strings::StaticName)**,
который содержит только хэш-сумму, но не саму строку. Используется хэш-функция
`fnv-1a64`, что позволяет вычислять хэш-суммы строк на этапе компиляции.

Движку всё же требуются полные строки, например, для вывода. Для этого
существует класс **[NameTable](@ref _16nar::strings::NameTable)**,
представляющий таблицу строк. При добавлении строки в таблицу выполняется
проверка на предмет коллизий хэша. Так как использование `StaticName`
неразрывно связано с использованием таблиц имён, это позволяет исключить
коллизии хэша или, в крайнем случае, обнаружить их и вывести ошибку.

В одной таблице имён содержатся строки, используемые в одном и том же
контексте. Но таких контекстов может быть несколько, например, имена
файлов ресурсов (один контекст) и имена типов для сериализации (другой
контекст). Логично, что нужно проверять коллизии только в рамках одного
и того же контекста, потому что использование строк из разных контекстов
не должно пересекаться, а также вполне допустимо, чтобы одна и та же
строка присутствовала в разных контекстах.

Для управления разными таблицами имён существует класс
**[NameManager](@ref _16nar::strings::NameManager)**, содержащий
разные таблицы имён и их собственные имена.

### System

В компоненте System содержится кросплатформенная обёртка над системными
функциями. Например, работа с файлами, загрузка динамических библиотек
и др.
